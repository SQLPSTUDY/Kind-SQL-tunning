# 데이터베이스 트랜잭션과 락

## 락과 트랜잭션

### 락(Lock)

동시성 제어를 위해 필요한 기능으로, 여러 커넥션에서 동시에 동일한 자원에 접근할 때 순서대로 한 시점에서는 하나의 커넥션만 변경할 수 있도록 보장하는 메커니즘입니다.

### 트랜잭션(Transaction)

논리적인 작업의 단위로, 논리적인 작업 셋을 모두 완벽하게 처리하거나(commit) 처리하지 못할 경우에는 원 상태로 복구(rollback)하여 부분 업데이트가 발생하지 않도록 데이터의 정합성을 보장합니다.

## 트랜잭션의 범위

### 트랜잭션 범위는 최소화하는 것이 좋습니다

**이유 1: DB Connection 제한**

- 트랜잭션 실행 시 DB connection이 필요
- 커넥션 개수는 제한되어 있음
- 각 프로그램이 커넥션을 소유하면 여유 커넥션 개수가 줄어듦
- 다른 프로그램에서 커넥션을 얻기 위해 대기해야 하는 상황 발생 가능

**이유 2: 외부 통신 의존성**

- 네트워크 통신과 같이 다른 서버와 통신하는 경우
- 외부 서버와 통신 장애 발생 시 DBMS 서버에도 높은 부하가 걸릴 수 있음
- 시스템 전체의 안정성이 위험해질 수 있음

## 트랜잭션의 ACID 속성

### Atomicity (원자성)

트랜잭션 중간에 어떠한 문제가 발생하면 트랜잭션에 해당하는 어떠한 작업 내용도 수행되어서는 안 되며, 아무런 문제가 발생하지 않았을 경우에만 모든 작업이 수행되어야 합니다.

### Consistency (일관성)

트랜잭션이 완료된 다음의 상태에서도 트랜잭션이 일어나기 전의 상황과 동일하게 데이터의 일관성을 보장해야 합니다.

### Isolation (고립성)

각각의 트랜잭션은 서로 간섭 없이 독립적으로 수행되어야 합니다.

### Durability (지속성)

트랜잭션이 정상적으로 종료된 다음에는 영구적으로 데이터베이스에 작업의 결과가 저장되어야 합니다.

## InnoDB 스토리지 엔진의 락

### 레코드 락 (Record Lock)

인덱스의 레코드에 대해 락을 거는 방식입니다. 레코드 자체가 아닌 인덱스에 락을 설정하며, 별도의 인덱스가 없다면 내부적으로 자체 생성된 클러스터 인덱스를 이용해 잠금을 설정합니다.

### 갭 락 (Gap Lock)

레코드와 레코드 사이의 간격에 새로운 레코드 생성을 제어합니다. 주로 넥스트 키 락의 일부로 사용됩니다.

### 넥스트 키 락 (Next-Key Lock)

레코드 락과 갭 락을 결합한 형태입니다.

### 자동증가 락 (Auto-Increment Lock)

새로운 레코드를 저장하는 INSERT나 REPLACE의 경우 발생하며, auto_increment를 일시적으로 막아주었다가 해제합니다.

## 트랜잭션 동시성 문제

여러 트랜잭션이 동시에 실행되면 동시성 제어 문제로 인해 데이터 불일치 현상이 발생할 수 있습니다.

### Dirty Read (더티 리드)

**현상**

- 한 트랜잭션이 아직 커밋되지 않은 데이터를 다른 트랜잭션이 읽는 상황
- 예시: A 트랜잭션이 데이터를 수정하고 아직 커밋하지 않은 상태에서 B 트랜잭션이 이 데이터를 읽으면, A가 롤백될 경우 B는 잘못된 데이터를 참조

**해결 방법**

- 격리 수준을 Read Committed로 설정

### Un-repeatable Read (반복 불가능 읽기)

**현상**

- 같은 데이터를 반복 조회할 때, 다른 트랜잭션이 해당 데이터를 수정하고 커밋하면서 결과가 달라지는 현상
- 예시: 트랜잭션 A가 데이터를 처음 조회했을 때와 두 번째 조회했을 때, 다른 트랜잭션 B가 데이터를 변경하고 커밋하면 A의 조회 결과가 달라짐

**해결 방법**

- 격리 수준을 Repeatable Read로 설정

### Phantom Read (팬텀 리드)

**현상**

- 동일한 조건으로 데이터를 조회했을 때, 다른 트랜잭션이 데이터를 삽입하여 조회 결과가 달라지는 현상
- 예시: 트랜잭션 A가 특정 조건으로 데이터를 조회했을 때, 트랜잭션 B가 새로운 데이터를 삽입하고 커밋하면 A가 같은 조건으로 다시 조회할 때 추가된 데이터가 나타남

**해결 방법**

- 격리 수준을 Serializable로 설정

## 트랜잭션 격리 수준 (Isolation Level)

트랜잭션 격리 수준은 여러 트랜잭션이 동시에 실행될 때 발생할 수 있는 데이터 불일치 문제를 제어하기 위한 설정입니다.

### Read Uncommitted

**특징**

- 커밋되지 않은 데이터도 읽을 수 있는 가장 낮은 격리 수준
- Dirty Read가 발생할 수 있음

### Read Committed

**특징**

- 커밋된 데이터만 읽을 수 있어 Dirty Read를 방지
- 반복 불가능 읽기는 발생할 수 있음

### Repeatable Read

**특징**

- 트랜잭션이 시작된 시점의 데이터를 기준으로 일관된 결과를 보장
- 반복 불가능 읽기를 방지
- InnoDB에서는 넥스트 키 락을 사용하여 Phantom Read도 방지 가능

### Serializable

**특징**

- 모든 트랜잭션을 순차적으로 실행하여 완벽한 일관성을 보장
- 가장 엄격한 격리 수준이지만 성능이 저하될 수 있음

## Read Committed vs Repeatable Read

### Read Committed

- 트랜잭션 중에 커밋된 데이터만 읽을 수 있음
- 다른 트랜잭션이 데이터를 수정하고 커밋하면 즉시 그 변경사항을 읽을 수 있음
- 동일한 데이터를 두 번 조회할 경우 결과가 달라질 수 있는 반복 불가능 읽기 발생

### Repeatable Read

- 동일 트랜잭션 내에서 동일한 데이터를 읽으면 항상 같은 결과를 반환
- 다른 트랜잭션이 데이터를 수정하고 커밋하더라도 현재 트랜잭션은 변경되기 전 데이터를 계속 읽음
- InnoDB에서는 넥스트 키 락을 사용하여 Phantom Read까지 방지

### 비교 예시

트랜잭션 A가 데이터를 조회한 후, 트랜잭션 B가 데이터를 수정하고 커밋하면

- **Read Committed**: 두 번째 조회 시 변경된 데이터를 읽음
- **Repeatable Read**: 첫 번째 조회와 같은 데이터를 반환

결과적으로 Repeatable Read는 더 높은 일관성을 보장하지만 성능 비용이 조금 더 발생할 수 있습니다.

## MVCC (Multi-Version Concurrency Control)

InnoDB의 MVCC, 즉 다중 버전 동시성 제어는 트랜잭션 간의 격리성을 보장하면서 성능을 높이기 위한 메커니즘입니다.

### 개념

트랜잭션이 데이터를 변경할 때 **변경 전 데이터를 언두 로그에 저장**하고, **변경 후 데이터를 InnoDB 버퍼 풀에 새로운 버전으로 관리**합니다. 이를 통해 각 트랜잭션은 자신의 격리 수준에 맞는 일관된 데이터를 읽을 수 있습니다.

### 동작 과정

**1단계: 트랜잭션 시작 및 데이터 변경**

- 각 트랜잭션에 고유한 트랜잭션 ID가 부여됨
- 데이터 변경 시 **COMMIT 여부와 무관하게 InnoDB 버퍼 풀이 먼저 새로운 값으로 갱신됨**
- 변경 전 데이터는 언두 로그에 복사되어 보관됨

**2단계: 데이터 읽기**

- **격리 수준에 따라 읽는 데이터가 달라짐**
    - READ_UNCOMMITTED: InnoDB 버퍼 풀의 최신 데이터를 읽음 (커밋 전이라도)
    - READ_COMMITTED 이상: 언두 로그를 통해 커밋된 데이터만 읽음
- 각 트랜잭션은 자신의 시작 시점이나 격리 수준에 맞는 데이터 버전을 읽음

**3단계: 트랜잭션 종료**

- **COMMIT 시**: 변경사항이 확정되고, InnoDB 버퍼 풀의 내용이 백그라운드 스레드를 통해 디스크에 기록됨
- **ROLLBACK 시**: InnoDB 버퍼 풀의 데이터가 언두 로그를 이용해 이전 상태로 복구됨
- 언두 로그는 더 이상 필요로 하는 트랜잭션이 없을 때 삭제됨

### 특징

- 읽기 작업에서 잠금을 걸지 않고도 읽기 일관성을 보장 (일반적인 RDBMS보다 빠른 성능)
- 언두 로그로 인해 추가적인 디스크 공간이 필요
- **사용하지 않는 언두 로그 데이터를 정리하는 시스템(Purge Thread)이 필요**
- **UNDO 블록 I/O, CR Copy 생성 등 부가적인 작업의 오버헤드 발생**
- 성능을 유지하면서도 트랜잭션 간 충돌을 최소화하고 격리성을 제공하는 효율적인 동시성 제어 방식

## Spring @Transactional의 격리 수준

### 기본 동작

Spring @Transactional은 기본적으로 데이터베이스의 기본 격리 수준을 따릅니다.

### isolation 속성 설정

`isolation` 속성을 사용해 명시적으로 격리 수준을 설정할 수 있습니다.

**설정 가능한 값**

- **DEFAULT**: 데이터베이스의 기본 설정을 따름
- **READ_UNCOMMITTED**: 커밋되지 않은 데이터를 읽을 수 있음
- **READ_COMMITTED**: 커밋된 데이터만 읽을 수 있음
- **REPEATABLE_READ**: 동일 트랜잭션 내에서 같은 데이터를 읽으면 일관된 결과를 반환
- **SERIALIZABLE**: 모든 트랜잭션을 순차적으로 실행하여 가장 높은 일관성을 보장
