# DML 튜닝

### DML 성능에 영향을 미치는 요소

1. 인덱스 
    - 정렬된 자료구조이기 때문에 삽입, 삭제 시 수직적 탐색을 통해 블록을 찾는다.
        - UPDATE는 삭제 후 삽입하는 방식으로 처리
        - TPS(Transaction Per Second)
2. 무결성 제약
    - 개체, 참조, 도메인, 사용자 정의
    - PK, FK가 Check, Not Null 제약보다 성능에 더 큰 영향을 미친다.
        - 실제 데이터를 조회해 봐야 하기 때문
3. 조건절
4. 서브쿼리
5. Redo 로깅
    - 트랜잭션을 재현하기 위해 모든 변경사항을 저장
6. Undo 로깅(Rollback)
    - 변경된 블록을 이전 상태로 되돌리는데 필요한 정보를 저장
7. Lock 
8. 커밋

**📔 Redo 로깅과 Undo 로깅**

| 구분 | **Redo**  | **Undo** |
| --- | --- | --- |
| **역할** | 커밋된 데이터를 **복구(재실행)** | 롤백 시 변경사항을 **되돌림** |
| **목적** | 시스템 장애 시 **커밋된 트랜잭션 복구** | 트랜잭션 실패 또는 ROLLBACK 시 **이전 상태로 복원** |
| **기록 시점** | 변경 **후(After Image)** 기록 | 변경 **전(Before Image)** 기록 |
| **주 사용 시점** | DB crash 후 **복구 시점** | 트랜잭션 중 **롤백 시점** |
| **복구 방향** | 앞으로(redo) → 다시 실행 | 뒤로(undo) → 취소 실행 |

**👍 실행 예시 :** `UPDATE 계좌 SET 잔액 = 잔액 - 10000` 실행했다고 가정

- **Undo 로그 작성**
    - 변경 전 값(`잔액 = 50000`)을 Undo 로그에 기록
        
        → 나중에 오류 시 되돌릴 수 있도록 “이전 상태” 저장
        
- **Redo 로그 작성**
    - 변경 후 값(`잔액 = 40000`)을 Redo 로그에 기록
        
        → 나중에 시스템 장애 시 다시 적용 가능
        

**📔 MVCC(Multi-Version Concurrency Control) 모델**

오라클에서 데이터를 읽는 두가지 방법

1. **Current** : 디스크에서 캐시로 적재된 원본 블록 Read
2. **Consistent** 
    - 쿼리 시작 이후, 변경된 블록(다른 트랜잭션으로 인한)을 만났을 때
    - 복사본 블록을 만든 후, Undo 데이터 적용
    - SCN(System Commit Number) : 마지막 커밋이 발생한 시점정보

블록 SCN : 마지막으로 변경된 시점

쿼리 SCN : Global 변수인 SCN 값을 먼저 확인하고 읽기 작업을 시작하는 것

즉, 블록 SCN이 쿼리 SCN보다 더 큰 블록을 만나면(마지막으로 변경된 시점이 더 최신화된 정보일 경우) 복사본을 만들고 Undo 데이터를 적용하여 쿼리가 시작된 시점으로 되돌려서 읽는다.

**👍  예시** 

| 시점 | 세션 A | 세션 B |
| --- | --- | --- |
| t1 (SCN=100) | `SELECT * FROM account;` 실행 |  |
| t2 (SCN=105) |  | `UPDATE account SET balance = balance - 100;` 실행 |
| t3 |  | `COMMIT;` |
| t4 | 세션 A의 SELECT는 여전히 “t1 시점의 snapshot”을 봄 |  |
- 세션 A는 t1 시점의 **Undo 로그 기반 복사본**을 읽음
- 세션 B가 나중에 데이터를 바꿔도, 세션 A의 쿼리 결과는 바뀌지 않음

**📔 커밋과 트랜잭션 동작과정**

Q. Redo 로그가 Append 방식으로 기록하더라도 디스크 I/O가 느린 이유는?

- 로그를 파일 끝에 순차적으로 덧붙이는 구조
- 단, Redo 로그도 파일이고 커밋 시점마다 반드시 디스크에 쓰기(Flush) 해야한다.
    - 랜덤 I/O를 줄이는 방식일지라도, 디스크 I/O를 없애는 방식은 아니다.

**Fast Commit** : Redo 로그를 이용한 논리적 커밋

- 커밋은 Redo 로그만 작성하고 끝낸 후, 추후 실제 데이터 파일에 천천히 반영

1. DML 실행 시, Redo 로그버퍼에 변경사항 기록
2. 버퍼 블록에서 데이터를 변경(버퍼캐시에 없다면, 데이터파일 읽는다.)
3. 커밋

DBWR, LGWR 프로세스는 **‘주기적으로’** 깨어나 각각 Dirty 블록과 Redo 로그버퍼를 파일에 기록한다.

**2-2. 수정 가능 조인 뷰**

**조인 뷰 :** FROM 절에 두개 이상 테이블을 가진 뷰

- 다른 테이블과 조인이 필요할 때 전통적인 UPDATE 문을 사용하면 비효율을 완전히 해소할 수 없다.

```sql
UPDATE 
(SELECT /*+ ordered use_hash(c) no_merge(t) */
			    c.최종거래일시, c.최근거래횟수, c.최근거래금액
       ,  t.거래일시,     t.거래횟수,     t.거래금액
  FROM   ( SELECT 고객번호
                , MAX(거래일시) 거래일시
                , COUNT(*)      거래횟수
                , SUM(거래금액) 거래금액
           FROM   거래
           WHERE  거래일시 >= TRUNC(ADD_MONTHS(SYSDATE, -1))
           GROUP BY 고객번호 ) t
  JOIN   고객 c
    ON   c.고객번호 = t.고객번호
)
SET    최종거래일시 = 거래일시
     , 최근거래횟수 = 거래횟수
     , 최근거래금액 = 거래금액;
```

- 바깥 UPDATE의 대상은 **인라인뷰(조인 결과)** 이지만, 실제로 갱신되는 표적은 **고객 c** 쪽 컬럼
- 조인은 인라인뷰 안에서 끝내고, **바깥에서 조인 2번 하지 않고 한 번에 갱신**
    - **참조 테이블을 두번 조인하는 비효율 제거**

### Direct Path I/O 활용

버퍼 캐시가 무조건 좋은게 아니다?

- 많은 데이터가 캐시를 방문하면, 오히려 버퍼 캐시에서 블록을 찾기 힘들 수 있다.
    - 버퍼캐시의 데이터가 자주 바뀌기 때문
- 예로, full sacn한 데이터는 재사용성이 낮은 데이터들인데 버퍼 캐시를 차지하면 안되겠지?

**Direct Path I/O :** 버퍼캐시를 경유하지 않고 데이터 블록을 읽고 쓰는 기능

ex) 병렬 쿼리 Full Scan, 병렬 DML, Direct Path Insert…

**Direct Path Insert**

1. Freelist 참조 없이 HWM 바깥 영역에 데이터를 순차적 입력
2. 블록을 버퍼캐시에서 탐색 및 적재 X
3. Undo 로깅 X 및 Redo 로깅 사용 안하게 할 수 있다. 
    
    (반면에 일반 INSERT는 로깅을 무조건 사용)
    

‼️ **주의할 점**

- Exclusive 모드 TM Lock
    - Table-level DML lock으로 테이블 객체에 거는 락
- 테이블 여유공간 활용 X

**병렬 DML**

**병렬 DML 활성화 방법 및 사용 방법**

```sql
// 활성화
alter session enable parallel dml;

// 힌트 사용
insert /*+ parallel(c 4) */ into 고객 c;
select /*+ full(o) parallel(o 4) */ * from 외부가입고객 o;
```

- 활성화 미설정시, 대상 레코드를 찾는 작업은 병렬로 진행하지만 추가, 변경, 삭제는 QC(Query Coordinator)가 혼자 담당한다.
- 실행계획에서 `PX COORDINATOR` 아래에 나타나야 병렬 DML이 동작한다.
    - 위에 나타날 경우, QC가 처리

**Prefixed vs Non-Prefixed**

- **Prefixed 인덱스**: **인덱스 선두 컬럼에 “파티션 키”가 포함**된 형태
    
    `LOCAL INDEX (신청일자, …)` 혹은 `LOCAL INDEX (신청일자, 신청순번)`
    
    - WHERE에 파티션 키 조건이 있으면 인덱스 차원에서 즉시 범위 축소
- **Non-Prefixed 인덱스**: 인덱스 **선두 컬럼이 파티션 키가 아님**
    
    `LOCAL INDEX (고객ID, 신청일자)` — 파티션 키 `신청일자`가 두 번째 이후
    
    - 인덱스 입장에서는 파티션 키가 필터로 적용
    - 인덱스 파티션을 여러 개 스캔해야 할 수 있고, 효율이 낮아진다.

**Q.Unique 인덱스를 파티셔닝하려면, 파티션 키가 모두 인덱스 구성 컬럼이어야 한다.** 

⇒ PK 인덱스가 파티셔닝키라면 특정 파티션만 탐색

⇒ 인덱스 구성 컬럼이 아닌 인덱스 파티셔닝을 할 경우, 모든 파티션을 탐색 

- 추가적인 Lock까지 발생시킨다.

- `ALTER TABLE … EXCHANGE PARTITION` 으로 **한 번에 교체**

### Lock과 트랜잭션 동시성 제어

**1. DML Row Lock(TX: 트랜잭션 락)**

- **Writer ↔ Writer**: 같은 행을 동시에 갱신하려 하면 **대기/경합**.
- **Reader ↔ Writer**: 일반 `SELECT`는 MVCC(Consistent Read) 로 과거 버전 읽으므로 서로 블로킹하지 않음.

**INSERT 경합 :** Unique 인덱스 검사(동일 키 동시 삽입 시 직렬화)

**2. Table Lock(TM:  테이블 락)**

- “이 테이블에 어떤 작업을 하고 있다” 라는 신호/플래그.
- 후행 트랜잭션이 이 신호를 바탕으로 **진행여부 결정**

**Lock을 풀기위한 방법 : 커밋**

- Blocking : 작업 진행 X
- 교착 상태 : 서로 다른 트랜잭션이 Lock 설정하려는 상황
    - Error Mesg 받은 트랜잭션이 롤백을 결정

**커밋 옵션 종류**

- **WAIT**: 잠금이 풀릴 때까지 대기
- **NOWAIT**: 잠금이 걸려 있으면 즉시 실패
- **IMMEDIATE**: 명령을 즉시 실행, 대기 없이 처리(주로 병렬/Direct Path에서 사용)
- **BATCH**: 작업을 모아 한 번에 처리해 I/O 효율 향상

**비관적 락 vs 낙관적 락**

**비관적 락**: 동시수행 할거지?

- 후행 트랜잭션이 기다린다.
- **방법**: 처리 전 **락 선점** → 후행 트랜잭션 **대기**.
    - 예: `SELECT … FOR UPDATE WAIT 5`
- **장점/단점**: 충돌 시 안전하지만 **대기·교착 가능**.

**낙관적 락: 동시수행 안할거지?**

> **직렬화(Serialization)** 는 필수다. 다중 트랜잭션 환경에서 공유자원 갱신은 어느 시점엔 순서를 정해야 데이터 무결성을 지킬 수 있다.
> 
> 
> (비관적 = DB가 직렬화, 낙관적 = 애플리케이션이 충돌 감지·해결)
> 

**채번(Numbering) 방식**

**1.  채번 테이블(키 테이블)**

- 테이블의 채번을 구분하는 값 ⇒ PK, 채번컬럼을 가지는 테이블을 만든다.
- 특정 테이블에서 INSERT
    - 특정 테이블을 가리키는 채번 값에 1을 더해 UPDATE

**2. 시퀀스(Sequence)**

- 테이블을 접근할때마다 채번이 1씩 자동 증가
    - **읽기만 해도 증가**(롤백해도 값은 소모됨)
- 단점 : 읽기만 해도 값이 증가
- 종류
    - 로우 캐시 Lock
    - 시퀀스 캐시 Lock
    - SV Lock

**3. MAX+1**

- 비권장하는 채번방식
    - `SELECT MAX(id)` + 1 은 **전체 스캔/락/경합** + **동시성 오류** 위험.
