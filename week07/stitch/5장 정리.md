# **소트 연산 최적화 정리**

## **1. 소트 수행 과정**

- **메모리 소트 (Internal Sort)**
    - PGA의 Sort Area만 사용하여 처리.
    - 데이터 양이 작을 때 빠름.
- **디스크 소트 (External Sort)**
    - Temp 테이블스페이스를 사용.
    - 데이터 양이 많으면 임시 세그먼트를 생성해 저장 (Sort run 단계) → 다시 머지(merge) → PGA로 적재.

👉 **결론**:

- 가능하다면 **소트 자체를 없애는 것**이 최선.
- 불가피하다면 **메모리 내에서 처리**되도록 유도해야 한다.

## **2. 실행계획에 나타나는 소트 연산 종류**

1. **Sort Aggregate**
    - 실제 정렬은 하지 않지만 Sort Area를 사용.
    - SUM, MAX, MIN, AVG 같은 집계 연산을 수행하면서 PGA에 적재.
2. **Sort Order By**
    - ORDER BY를 위한 정렬 수행.
3. **Sort Group By**
    - 그룹 집계를 위해 소팅 알고리즘 사용.
    - Oracle은 **Hash Group By** 로도 최적화할 수 있음.
4. **Sort Unique**
    - DISTINCT, UNION 중복 제거 시 수행.
5. **Sort Join**
    - Sort Merge Join 과정에서 정렬 수행.
6. **Window Sort**
    - 윈도우 함수(Row_number, Rank 등) 실행 시 정렬 수행.

## **3. 소트를 피하는 SQL 작성법**

### **(1) UNION → UNION ALL**

- UNION 은 중복 제거를 위해 전체 레코드를 정렬 → 소트 발생.
- UNION ALL 은 단순 병합 → 소트 불필요.
- 단, 결과 집합에 중복이 생길 수 있으므로 데이터 요건 확인 필요.

### **(2) DISTINCT 피하기**

- DISTINCT 는 중복 제거를 위해 전체 범위를 정렬해야 함 → **부분 범위 처리 불가**.
- 대체: EXISTS 사용

```sql
SELECT 1
FROM 고객 c
WHERE EXISTS (
  SELECT 1 FROM 거래 t
  WHERE t.고객ID = c.고객ID
)
```

- MINUS 는 두 집합 차집합을 반환하는 집합 연산.
- 동일 로직을 원한다면 NOT EXISTS로 변환 가능하지만, **NULL 처리와 중복 처리 차이**가 있음 → SQL 요구사항 따라 선택.

### **(3) 조인 방식 변경**

```sql
SELECT c.계약번호, c.상품코드, p.상품명
FROM 계약 c, 상품 p
WHERE c.지점ID = :brch_id
  AND p.상품코드 = c.상품코드
ORDER BY c.계약일시 DESC
```

- [지점ID + 계약일시] 인덱스를 만들면 정렬을 피할 수 있음.
- 하지만 Hash Join 은 조인 후 정렬이 다시 필요 → 소트 발생.
- **NL Join** 사용 시 인덱스의 정렬 상태를 그대로 활용 가능 → 소트 생략 가능.

## **4. 인덱스를 이용한 소트 생략**

### **Top N 쿼리**

```sql
SELECT *
FROM (
  SELECT 거래일시, 체결건수, 체결수량, 거래대금
  FROM 종목거래
  WHERE 종목코드 = 'KR123456'
    AND 거래일시 >= '20180304'
  ORDER BY 거래일시
)
WHERE ROWNUM <= 10
```

- [종목코드 + 거래일시] 인덱스 → ORDER BY 불필요, 소트 생략.
- 실행계획에 **COUNT STOPKEY** 등장 → 지정 건수만큼 읽고 즉시 멈춤.

👉 **Top N Stopkey 알고리즘**: 결과 일부만 반환할 때 전체 정렬을 하지 않고 인덱스 순서대로 제한된 개수만 읽어오는 방식.

### 페이징 처리

```sql
SELECT *
FROM (
    SELECT ROWNUM no, a.*
    FROM (
        /* SQL Body */
    ) a
    WHERE ROWNUM <= (:page * 10)
)
WHERE no >= (:page - 1) * 10 + 1
```

- ROWNUM 을 중첩 Subquery에서 먼저 제한해야 **부분 범위 처리** 가능.
- ROWNUM 제한 없이 BETWEEN 만 쓰면 전체를 다 읽은 후 걸러내야 하므로 Stopkey 최적화가 적용되지 않음.

### **MIN / MAX 최적화**

- 인덱스의 선두 컬럼이 조건절에 있고, MIN/MAX 대상 컬럼도 인덱스에 포함되어 있으면 → 인덱스만으로 최소/최대값 탐색 가능.
- 이 경우 불필요한 테이블 액세스 없이 빠르게 결과 반환.
- 조건절 컬럼과 MIN/MAX 함수 인자 컬럼이 모두 인덱스에 포함되어 있어야 함. 아니면 테이블 액세스 발생

👉 여기서도 내부적으로는 **First Row Stopkey 알고리즘**이 활용됨.

# **Sort 연산을 줄이기 위한 심화 정리**

## **1. Sort Area 최소화 전략**

소트 연산이 불가피하다면 **Sort Area(PGA 메모리)** 내에서 끝내야 한다.

Temp 테이블스페이스를 쓰게 되면 디스크 I/O가 발생하여 성능이 급격히 저하된다.

```sql
select lpad(상품번호, 30) || lpad(상품명, 30) || lpad(고객ID, 10)
     || lpad(고객명, 20) || to_char(주문일시, 'yyyymmdd hh24:mi:ss')
from 주문상품
where 주문일시 between :start and :end
order by 상품번호
```

```sql
select lpad(상품번호, 30) || lpad(상품명, 30) || lpad(고객ID, 10)
     || lpad(고객명, 20) || to_char(주문일시, 'yyyymmdd hh24:mi:ss')
from (
    select 상품번호, 상품명, 고객ID, 고객명, 주문일시
    from 주문상품
    where 주문일시 between :start and :end
    order by 상품번호
)
```

- 1번 SQL은 모든 컬럼을 가공해서 Sort Area에 올림 → 메모리 사용량 큼.
- 2번 SQL은 **원본 상태에서 정렬 후 마지막에 가공** → Sort Area 사용량 작음.
- 실행계획 비교 시 1번은 716MB, 2번은 17MB 사용.
    
    👉 **정렬 컬럼만 Sort Area에 두는 방식**으로 작성하는 것이 유리하다.
    

## **2. Top N 쿼리의 소트 최적화 (Stopkey 알고리즘)**

### **개념**

- ROWNUM 또는 FETCH FIRST n ROWS ONLY 같은 조건이 있으면, 오라클은 **Top N Stopkey 알고리즘**을 사용.
- 전체를 다 정렬하지 않고, **필요한 개수만큼만 Sort Area에서 관리**한다.

```sql
select *
from (
    select 거래일시, 체결건수, 체결수량, 거래대금
    from 종목거래
    where 종목코드 = 'KR123456'
      and 거래일시 >= '20180304'
    order by 거래일시
)
where rownum <= 10
```

- 실행계획에 SORT ORDER BY STOPKEY 등장.
- 10건까지만 Sort Area에 유지하고 이후는 무시 → 메모리 절약.
- AutoTrace 결과에서도 **disk sort 발생 없음**.

### **⚠️ 주의**

ROWNUM 조건을 빼고 단순히 BETWEEN 같은 조건만 쓰면 Stopkey 최적화가 사라짐 → 전체 정렬 발생.

### **3. Top N 쿼리가 아닐 때 발생하는 부하**

```sql
select *
from (
    select rownum no, a.*
    from (
        select 거래일시, 체결건수, 체결수량, 거래대금
        from 종목거래
        where 종목코드 = 'KR123456'
          and 거래일시 >= '20180304'
        order by 거래일시
    ) a
)
where no between (:page-1)*10+1 and (:page*10)
```

- 여기서는 ROWNUM 제약이 바깥에만 걸려있음.
- 실행계획에서 STOPKEY 사라짐 → 전체 정렬 수행.
- AutoTrace 결과 sorts (disk) 발생 → Temp 테이블스페이스 사용.

👉 페이징 처리 시 반드시 **중첩 Subquery 안에서 ROWNUM으로 제한**해야 Stopkey 적용 가능.

## **4. 분석 함수와 Top N Sort**

- **MAX/MIN 함수**는 단순 집계 연산 → 인덱스 포함 여부에 따라 빠르게 처리 가능.
- **하지만 Window 함수(MAX() OVER, RANK(), ROW_NUMBER())** 는 파티션 단위로 정렬을 수행해야 하므로 Sort 발생.

### **결과**

- MAX() OVER(PARTITION ...) 사용 시: **Window Sort 발생** → 많은 physical read/write.
- RANK() OVER(...) 사용 시: 실행계획에서 **WINDOW SORT PUSHED RANK** 등장.
    - 물리 I/O는 여전히 발생했으나, MAX() 보다 훨씬 줄었고 성능 개선됨.

👉 **이유**:

- MAX() 집계 함수는 전체 파티션을 다 읽고 마지막 값만 반환.
- RANK() + ROW_NUMBER() 는 **Top N Stopkey와 유사하게 앞부분에서 잘라낼 수 있음** → 더 효율적.
