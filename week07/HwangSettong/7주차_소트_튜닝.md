## 5.1 소트 연산에 대한 이해

### 5.1.1 소트 수행 과정

- **소트 유형**
    - In-Memroy Sort (Internal Sort)
        
        전체 데이터 정렬 작업을 메모리 공간인 Sort Area 내에서 완료하는 것
        
    - To-Disk Sort (External Sort)
        
        Sort Area 내에서 정렬하지 못해, 디스크 공간까지 사용하게 되는 경우
        

- **소트 과정**

    4. Sort Run : 양이 많을 때는 중간 정렬된 집합을 Disk의 Temp 스페이스에 임시 세그먼트를 만들어 저장
    5. Sort Merge : Temp 스페이스에 정렬된 순서대로 PGA에서 읽어 Merge

- 성능
    - **메모리 집약적 (Memory-intensive)**
        
        정렬을 하려면 데이터를 임시로 잡아두고 정렬 알고리즘을 적용하기 위해, Sort Area라는 메모리 공간을 만들어서 데이터를 올려두고 비교/교환 작업을 함. 만약 정렬해야 할 데이터가 메모리에 다 안 들어가면, 디스크 TEMP 공간을 쓰게 되고, 이건 성능을 크게 떨어뜨림. 즉, 정렬은 데이터를 메모리에 한 번에 담을 수 있느냐 없느냐가 성능에 직결.
        
    - **CPU 집약적 (CPU-intensive)**
        
        정렬 알고리즘 자체가 많은 비교 연산과 교환 작업을 필요로 함. 데이터 건수가 커질수록 비교 연산 횟수가 폭증하니 CPU 사용률이 올라감.
        
    - **부분범위처리 방해**
        
        `ORDER BY` + `LIMIT` 같은 요청을 했을 때, 인덱스를 이용하면 처음부터 정렬된 순서대로 데이터를 꺼낼 수 있으니까 10개 뽑자마자 바로 응답 가능. 반면 정렬을 해야 하면 전체 결과 집합을 다 정렬해야 앞의 10개도 알 수 있음. → 끝까지 다 정렬해야 결과가 나옴.
        

### 5.1.2 소트 오퍼레이션

- Sort Aggregate
    
    전체 로우를 대상으로 sum, min, max, count 같은 집계를 수행할 때 나타남.
    
    실제로 정렬을 하지는 않지만 전체 데이터를 읽어 비교함.
    

- Sort Order By
    
    데이터 정렬할 때 나타남 (order by)
    
- Sort Group By
    
    그룹별 집계를 수행할 때 데이터를 그룹별로 묶기 위해 정렬
    
    (10gR2 버전 부터는 group by 절 뒤에 order by 쓰지 않으면 Hash Group By로 처리 ← temp table space 사용 안함)
    

- Sort Unique
    
     DISTINCT 또는 집계 함수의 그룹핑 없이 고유 값만 필요할 때 나타남
    
    정렬 후 중복 제거하기 때문
    
    (10gR2 버전 부터는 order by 쓰지 않으면 Hash Unique로 처리 ← temp table space 사용 안함)
    
- Sort Join
    
    소트 머지 조인 수행 시 나타남 (ordered use_merge(e))
    

- Window Sort
    
    분석 함수 사용할 때 나타남
    

## 5.2 소트가 발생하지 않도록 SQL 작성

### 5.2.1 Union vs. Union All

Union 사용 시 두 집합의 중복 제거를 위해 소트 연산을 수행하게 됨.

만약 두 집합이 **상호배타적**이라면, 무조건 **Union All**을 사용하는게 성능에 좋음.

```sql
select 결제번호, 결제수단코드, 주문번호, 결제금액, 결제일자, 주문일자
  from 결제
 where 결제일자   = '20180316'
union all
select 결제번호, 결제수단코드, 주문번호, 결제금액, 결제일자, 주문일자
  from 결제
 where 주문일자   = '20180316'
   and (결제일자 <> '20180316' or 결제일자 is null)
```

소트 연산을 생략하기 위해 Union All을 사용하면서 중복을 피하기 위해 위의 쿼리와 같이 배타적인 조건절을 추가해주는 방법도 있음.

### 5.2.2 Exists 활용

DISTINCT나 MINUS를 사용하게 되면 중복 제거를 위해 Hash를 쓰거나 소트 연산이 일어나게 됨. Hash 테이블을 사용하거나 소트 연산이 수행되면 부분범위처리가 불가능해짐. 때문에 대신 EXISTS를 사용하는게 좋음.

```sql
SELECT DISTINCT i.item_cd, i.item_nm, i.price, ...
  FROM item i, contract c
 WHERE i.item_cls_cd = :iclscd
   AND c.item_cd     = i.item_cd
   AND c.ctr_dt BETWEEN :dt1 AND :dt2
   AND c.ctr_typ_cd  = :ctpcd
```

```sql
SELECT i.item_cd, i.item_nm, i.price, ...
  FROM item i
 WHERE i.item_cls_cd = :iclscd
   AND c.item_cd     = i.item_cd
   AND EXISTS (SELECT 'x'
						     FROM contract c  
							  WHERE c.item_cd     = i.item_cd
					        AND c.ctr_dt BETWEEN :dt1 AND :dt2
					        AND c.ctr_typ_cd  = :ctpcd)
```

EXISTS를 사용하면 데이터의 존재 여부만 파악하기 때문에 조건절을 만족하는 데이터를 모두 읽지 않아도 됨. item 테이블에 대하여 부분범위처리도 가능.

### 5.2.3 조인 방식 변경

```sql
-- 계약 인덱스가 지점ID+계약일시 일 때
select c.계약번호, c.상품CD, p.상품명, p.상품구분, c.계약금액, c.계약일시
from 계약 c, 상품 p
where c.지점ID = :brch_cd
  and p.상품CD = c.상품CD
order by c.계약일시 desc
```

위 쿼리에서 `지점ID = :brch_cd` 조건을 만족하는 row들을 `계약일시` 순으로 이미 정렬된 상태로 뽑아올 수 있음에도 불구하고, 옵티마이저가 Hash 조인을 선택하게 되면 정렬이 필요하게 된다. (Hash 조인은 순서를 보장하지 않음)

때문에, `/*+ leading(c) use_nl(p) */` 힌트를 주어 NL조인을 유도하는 것이 좋다.

## 5.3 인덱스를 이용한 소트 연산 생략

### 5.3.1 Sort Order By 생략

```sql
select 거래일시, 체결건수, 체결수량, 거래대금
from 종목거래
where 종목코드 = '12345'
order by 거래일시
```

- 인덱스를 [종목코드] 만으로 구성했다면? 소트 연산을 생략할 수 없음
    
    인덱스는 ‘종목코드’로 정렬되어 있음. `WHERE 종목코드 = '12345'` 조건에 맞는 레코드를 찾을 때는 유리
    
    하지만 인덱스 안에서 동일한 ‘종목코드’의 레코드들은 ‘**거래일시’ 기준으로 정렬돼 있지 않음**
    
    → 디스크상의 물리적 순서대로 흩어져 있음.
    
- 인덱스를 [종목코드 + 거래일시] 로 구성했다면? 소트 연산 생략 가능
    
    인덱스는 `(종목코드 ASC, 거래일시 ASC)` 순으로 정렬되어 저장됨.
    
    따라서 `종목코드='12345'`에 해당하는 구간 스캔을 하면 그 안에서 이미 **거래일시 순서**가 보장
    

### 5.3.2 Top N 쿼리

- 3-Tier 환경에서 부분범위 처리를 활용한 튜닝 기법 : Top N 쿼리
    
    <aside>
    
    **부분범위 처리(PRP)**
    
    대량 데이터를 한 번에 다 가져오지 않고, **사용자가 보는 화면 단위(예: 10건, 20건)** 만큼만 끊어서 가져오는 방식
    
    **부분범위 처리의 특징**
    
    1. 결과 집합 출력을 바로 시작할 수 있는가?
    2. 앞쪽 일부만 출력하고 멈출 수 있는가?
    </aside>
    
    3-Tier (= Client ↔ WAS ↔ DB) 환경 특징
    
    - Client는 DB에 직접 붙지 않고 WAS랑만 통신. DB에서 데이터가 WAS로 오고 Client(브라우저/앱)에는 WAS가 잘라서 내려주는 구조가 됨. → Client 단에서의 PRP 필요성이 줄어듦.
    - Client가 DB 커넥션 독점 불가
        
        단위 작업을 마치면 DB 커넥션을 바로 커넥션 풀에 반환해야 하므로 그 전에 조회 결과를 Client에게 모두 전송하고 Cursor를 닫아야 함. → 쿼리 결과 집합을 조금씩 나눠서 전송하는 방식 사용 불가
        
    
    하지만, WAS ↔ DB 사이에서는 여전히 대량 데이터 전송이 있을 수 있기 때문에 부분범위 처리는 여전히 중요하고, **Top N 쿼리** 같은 튜닝 기법으로 활용
    

Top N 쿼리란, 전체 결과 집합 중 상위 N개 레코드만 선택하는 쿼리.

Oracle에서는 인라인 뷰로 한번 감싸서 사용 가능

```sql
select *
from (
     select 거래일시, 체결건수, 체결수량, 거래대금
     from 종목거래
     where 종목코드  = '12345'
       and 거래일시 >= '20180304'
     order by 거래일시
)
where rownum <= 10
```

이 때도 [종모코드 + 거래일시] 로 인덱스를 구성하여 소트 연산을 생략하게 하면 인덱스를 스캔하다가 열 개 레코드를 읽는 순간 바로 멈추게 됨.

- **실행계획의 `COUNT(STOPKEY)`**
    
    조건절에 부합하는 레코드가 아무리 많아도 ROWNUM으로 정한 건수만큼 결과 레코드를 얻으면 거기서 바로 멈춤 stopkey
    
- **페이징 처리**
    
    ```sql
    select *
    from (
         select rownum no, a.*
         from (
    			     /* SQL BODY */
    		 ) a
         where rownum <= (:page * 10) /*여기가 stopkey 핵심!*/
    )
    where no >= (:page-1)*10 + 1
    ```
    

### 5.3.3 최소값/최대값 구하기

min / max 구하는 실행계획에는 `Sort Aggregate`가 있다. 만약 최소/최대 값을 찾을 데이터를 인덱스 적용하면, `INDEX (FULL SCAN (MIN/MAX))` 와 같은 실행계획이 나타난다.

전체 데이터를 읽지 않고 인덱스를 이용해 최소/최대 값을 구하려면, 조건절 컬럼과 MIN/MAX 함수 인자 컬럼이 모두 인덱스에 포함되어 있어야 한다.

**실행계획의 `FIRST ROW`  :** 조건을 만족하는 레코드 하나를 찾았을 때 바로 멈춤 = first row stopkey

만약 인덱스에 조건절 컬럼과 MIN/MAX 함수 인자 컬럼 중 하나라도 없으면, first row stopkey 작동 안함.

그럴 땐 `WHERE ROWNUM <= 1;` 과 같이 Top N으로 레코드를 찾을 수 있음.

### 5.3.4 이력 조회

최신 이력 데이터를 조회할 때 first row stopkey나 top n stopkey가 잘 작동할 수 있도록 해야함.

`INDEX_DESC` 힌트를 사용하고, ROWNUM ≤ 1 조건절을 사용하여 부분범위 처리

- 일반 ORDER BY 변경일시 DESC
    
    → 전체 레코드 읽고 정렬 후 → 첫 건 반환 (비효율)
    
- INDEX_DESC + ROWNUM = 1
    
    → 최신 건만 딱 찾아내고 멈춤 (효율 극대화)
    

전체 이력 조회를 할 때는 stopkey 가 핵심 요소가 아님. 윈도우 함수, `KEEP` 절 이용하는게 효과적

기간(From~To)을 선분처럼 관리하는 선분 이력 구조는 쿼리를 더 간단히 할 수 있고 성능 측면에서도 효과적

### 5.3.5 Sort Group By 생략

```sql
-- 인덱스 : REGION
SELECT REGION, AVG(AGE), COUNT(*)
FROM CUSTOMER
GROUP BY REGION
```

- GROUP BY에 선두 컬럼 인덱스가 있다면, Sort Group By 연산을 생략 가능.
- 실행계획에 `Sort Group By Nosort`라고 표현됨

## 5.4 Sort Area를 적게 사용하도록 SQL 작성

### 5.4.1 소트 데이터 줄이기

1. select 절에 가공되지 않은 데이터 사용
2. select 절에 필요한 데이터만 사용

### 5.4.2 TOP N 쿼리의 소트 부하 경감 원리

TOP N 쿼리는 정렬을 전부 하지 않고, 상위 N건만 유지하는 방식으로 동작.

필요 없는 뒷부분 정렬은 버리므로 소트 부하가 대폭 경감됨.

인덱스를 활용해 정렬 자체를 피해 최적화 할 것.

### 5.4.3 TOP N 쿼리가 아닐 때 발생하는 소트 부하

```sql
select *
from (
     select rownum no, a.*
     from (
			     /* SQL BODY */
		 ) a
)
where no between (:page-1)*10 + 1 and (:page*10)
```

`where rownum <= (:page * 10)` 를 제거하고 위와 같이 쿼리를 수행할 때

DB는 내부 SQL 결과 전체를 읽고 rownum 부여 → 필요한 구간만 반환

따라서 TOP N Stopkey 최적화 적용 불가(실행계획에 `STOPKEY` 표시 안 됨)

데이터가 많으면 메모리를 초과 → 디스크 임시 테이블 사용 → I/O 부하 발생

### 5.4.4 분석함수에서의 TOP N 소트

`ROW_NUMBER()`, `RANK()`, `DENSE_RANK()` 등 분석 함수를 사용하는 경우

(Oracle 12c 이상에서는 TOP N 알고리즘을 분석 함수와 결합함)

각 파티션에서 상위 N건만 유지하면서 정렬 → 불필요한 정렬 최소화

`MAX`, `MIN` 같은 집계 함수보다 메모리와 정렬 비용을 줄일 수 있음
