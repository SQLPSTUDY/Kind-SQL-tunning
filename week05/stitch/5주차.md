# 인덱스 튜닝

## 1. 테이블 액세스 최소화

**ROWID :** 포인터, 물리적 주소가 아닌 테이블 레코드를 찾아가기 위한 논리적인 주소 정보

- 동작과정
    - ROWID가 가리키는 테이블 블록을 버퍼캐시에서 먼저 찾아보고, 못 찾을 때만 디스크에서 블록을 읽는다.

**TABLE ACCESS (BY INDEX ROWID)** 는 **인덱스를 통해 ROWID(행의 물리적 주소)를 얻은 후, 해당 행을 실제 테이블에서 읽어오는 방식**

### 1-1. 인덱스 클러스터링 팩터(CF)

**특정 컬럼을 기준으로 같은 값을 갖는 데이터가 서로 모여있는 정도를 의미한다.** 

⇒ 인덱스 순서와 테이블 물리적 저장 순서의 일치 정도

Q. 인덱스 레코드마다 테이블 레코드를 블록 단위로 I/O하면 CF가 의미가 있나?

⇒  **버퍼 Pinning:**  래치 획득, 해시 체인 스캔 과정을 거쳐 어렵게 찾아간 테이블 블록에 대한 포인터를 바로 해제하지 않고 유지

⇒ 즉, 래치 획득, 해시 체인과정을 생략할 수 있다. 

**인덱스 손익분기점** 

Table Full Scan : 시퀀셜 액세스 + Multi Block I/O

Table Access By Index Scan : 랜덤 액세스 + Single Block I/O

인덱스 스캔의 손익 분기점은 일반적으로 5~20%, CF에 따라 손익분기점이 달라진다. 

### 1-2. 인덱스 컬럼 추가

- 조건절에 있는 컬럼을 인덱스 컬럼에 추가하여 랜덤 액세스 횟수를 줄일 수 있다.

### 1-3. 인덱스만 읽고 처리

```sql
create index emp_x01 on emp (deptno) include (sal)
```

- SAL 컬럼을 리프 블록에 저장하여, 랜덤 액세스 횟수를 줄일 수 있다.
    - 만약 sal 컬럼을 조회할 경우, 테이블 액세스가 아닌 리프 블록에서 sal 값을 가져오기 때문이다.
- 하지만, 인덱스 컬럼에 추가된 것은 아니기 때문에 추가할 경우가 스캔량이 더 적다.

### 1-4. 인덱스 구조 테이블

**IOT(Index-Organized Table)**

인덱스 리프 블록이 곧 데이터 블록

- 데이터 입력시, 랜덤 방식을 사용하는 힙 구조 테이블과 다르게(Freelist로부터 할당 받은 블록에 정해진 순서없이 입력) 정렬 상태를 유지하며 데이터를 입력한다.

### 1-5. 클러스터 테이블

**인덱스 클러스터**: 여러 테이블을 키 기준으로 같은 블록 → 조인 최적화

**해시 클러스터**: 해시로 바로 블록을 찾아가는 구조 → 단건 조회 최적화

## 3. 인덱스 스캔 효율화

### **1. 액세스 조건 vs 필터 조건**

- **액세스 조건 (Access Predicate)**
    - 인덱스를 스캔하는 단계에서 처리되는 조건.
    - **스캔 범위를 결정**하는 조건절로, 인덱스의 수직적 탐색 및 스캔 Stop 여부에 영향을 미침.
    - 인덱스의 장점을 100% 활용할 수 있는 조건.
- **필터 조건 (Filter Predicate)**
    - 인덱스를 통해 얻은 ROWID로 테이블에 액세스한 후 처리되는 조건.
    - 테이블 블록에서 행을 가져온 뒤, 결과 집합에 포함할지 여부를 결정.
    - 인덱스 단계에서 소거되지 못하고 테이블까지 접근해야 하므로 비효율적일 수 있음.

👉 **정리**: 인덱스를 최대한 활용하려면 조건을 **액세스 조건**으로 만드는 것이 중요하다.

### **2. 인덱스 선행 컬럼 유무**

1. 인덱스의 **선행 컬럼**이 등치 조건(=)이 아닐 경우 → 비효율적 스캔 발생.
    - 예: WHERE col1 > 100 → 선행 컬럼이 범위 조건이면 이후 컬럼은 액세스 조건으로 쓰이지 못함.
2. **엑세스 조건 vs 필터 조건** 구분에 따라 성능 차이가 커짐.

### **3. 효율화 기법**

**(1) BETWEEN → IN-LIST 전환**

- **원리**: BETWEEN 범위 조건을 IN 조건으로 나눠주면, 각각이 등치 조건처럼 동작.
- 오라클은 내부적으로 UNION ALL 로 변환해 실행.
- 장점: 선행 컬럼이 범위 스캔일 때 발생하는 비효율이 사라짐.
- 단점: IN 항목 개수가 많으면 오히려 비효율적 (매 항목마다 블록 탐색 필요).
- **적용 시점**: 데이터가 넓게 분포되어 있고, 범위 스캔으로는 I/O가 과다할 때.

---

**(2) 인덱스 스킵 스캔**

- 인덱스 **선두 컬럼이 조건절에 없더라도** 후속 컬럼을 이용해 인덱스를 사용할 수 있는 기법.
- 선두 컬럼의 **distinct 값이 적을 경우** 유용.
- 내부적으로 선두 컬럼 값 집합을 가정하여 여러 번 인덱스를 탐색.
- 예: 인덱스 (gender, name) 존재 시 → WHERE name = 'Kim' 조건에서도 스킵 스캔 가능 (gender 값이 소수이면 효과적).

---

**(3) OR 조건 활용법**

- **주의**: 인덱스 선두 컬럼에 OR 사용은 피해야 함.
    - 선두 컬럼이 액세스 조건이 아닌 경우 → 이후 조건들이 모두 필터 조건으로 밀려남.
- 활용: 인덱스에 포함되지 않은 컬럼에 대한 옵션 조건에서만 OR 사용.
    - 이 경우 테이블 필터 조건에서만 처리 가능.
- 단, 인덱스 구성 컬럼 중 하나 이상이 **NOT NULL 컬럼**이면 → 인덱스 필터 조건에서 일부 활용 가능.

---

**(4) LIKE / BETWEEN 최적화**

- 인덱스 효율을 위해 조건 컬럼의 순서 및 특성을 고려해야 함.
1. 선두 컬럼이 인덱스에 포함되어야 함.
2. NULL 허용 컬럼은 LIKE 조건 이후에만 유효.
3. 숫자형 컬럼은 범위 조건(BETWEEN)에 유리.
4. 가변 길이 컬럼(VARCHAR2)은 LIKE 조건에서 인덱스를 활용할 수 있음.

**(5) UNION ALL 활용**

```sql
select * from 거래
where :cust_id is null
and 거래일자 between :dt1 and :dt2
union all
select * from 거래
where :cust_id is not null
and 고객ID = :cust_id
and 거래일자 between :dt1 and :dt2
```

- 조건에 따라 실행 계획을 분리함으로써 불필요한 조건 평가 제거.
- cust_id가 NULL인 경우와 아닌 경우를 나누어 처리하면 옵티마이저가 더 정확한 실행 계획 선택 가능.
- 특히 인덱스 액세스 조건을 보장할 수 있어 효율적.

**(6) NVL/DECODE**

```sql
select * from 거래
where 고객ID = nvl(:cust_id, 고객ID)
and 거래일자 between :dt1 and :dt2

select * from 거래
where 고객ID = decode(:cust_id, null, 고객ID, :cust_id)
and 거래일자 between :dt1 and :dt2
```

- NVL/DECODE 조건 → 옵티마이저가 **Or Expansion 쿼리 변환** 수행.
    - 바인드가 NULL인 경우 (조건 무효화)
    - 바인드가 NOT NULL인 경우 (인덱스 조건 사용 가능)

## 4. 인덱스 설계

**두가지 선택 기준**

- 조건절에 항상 사용하거나, 자주 사용하는 컬럼 선정
- ‘=’ 조건으로 자주 조회하는 컬럼을 앞쪽에 둔다.

스캔 효율성 이외의 판단 기준

- 수행 빈도
- 업무상 중요도
- 클러스터링 팩터(CF)
- 데이터량
- DML 부하
- 저장 공간
- 인덱스 관리 비용

### 소트 연산을 생략하기 위한 컬럼 추가

```sql
SELECT  계약일자,청약일자,입력자ID,계약상태코드,보험시작일자,보험종료일자
FROM    계약
WHERE   취급지점ID = :trt_brch_id
AND     청약일자 BETWEEN :sbcp_dt1 AND :sbcp_dt2
AND     계약일자 > TRUNC(SYSDATE - 3)
AND     계약상태 IN (:ctr_stat_cd1, :ctr_stat_cd2, :ctr_stat_cd3)
ORDER BY 청약일자, 입력자ID;

```

- 인덱스는 항상 정렬된 상태를 유지하기 때문에 “청약일자+입력자ID” 순서로 인덱스를 설계해도 Sort연산을 생략할 수 있다.
- “=” 조건절은 인덱스 컬럼 어디든 위치해도 괜찮지만, “=”가 아닌 조건절은 반드시 ORDER BY 뒤쪽에 있어야 한다.

**I/O 최소화하며 SORT연산을 생략하기 위해서는?**

1. “=” 연산자로 사용한 조건절 컬럼 선정
2. ORDER BY 절에 기술한 컬럼 추가
3. “=” 연산자가 아닌 조건절 컬럼은 데이터 분포를 고려해 추가 여부 결정

👉 **[취급지점ID + 청약일자 + 입력자ID]** 

### 결합 인덱스 선택도

**1. 선택도(Selectivity)와 카디널리티(Cardinality)**

- 인덱스를 만들 때는 반드시 **선택도**(조건으로 걸렀을 때 얼마나 줄어드느냐)와 **카디널리티**(컬럼 값의 다양성)를 확인해야 한다.
- 선택도가 높은 컬럼(즉, 조건 걸면 결과가 적게 나오는 컬럼)이 인덱스 효율을 높인다.

**2. 컬럼 순서 결정**

- 결합 인덱스에서 **컬럼 순서**는 일반적으로 큰 영향을 미치지 않는다.
    - 예: `고객번호`, `성별`을 어떻게 배치하든 `=` 조건이면 인덱스 스캔 범위는 동일하다.
- 하지만 원칙은 있다:
    - **항상 사용하는 컬럼**을 앞쪽에 둔다.
    - `=` 조건 컬럼을 선두에 두는 것이 일반적이며, 범위 조건(<, >, BETWEEN 등)은 뒤쪽에 두는 것이 좋다.

**정리**

- **고객번호와 고객등급** 모두 '=' 조건이라면 어느 쪽을 앞에 두든 상관없음.
- 하지만 범위 검색 컬럼(거래일자 등)은 '=' 조건 뒤에 둬야 인덱스 효율이 높다.
- 인덱스 압축(compression)을 고려하면 선택도가 낮은 컬럼(예: 고객등급)을 앞에 두는 것이 유리할 때도 있다.
- 결론적으로, 인덱스 설계 시 **선택도 자체보다 더 중요한 건 '항상 사용되는 컬럼' 여부와 연산자 형태**다.
